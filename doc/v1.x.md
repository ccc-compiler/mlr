# 設計提案：MLR v1.x 路線

> **基線：v1.0。** 語言、五階段編譯器、CPU／Metal Performance Shaders 兩套
> runtime、`value_and_grad` 訓練、編譯期（`mlr.load`）與執行期
> （`mlr.load_runtime`）權重載入、`save_pt` 均已可用；`scripts/run_all.sh`
> 的 14 個範例 × 2 runtime 與 `cargo test` 全綠。
>
> **原則：** v1.x 只做「會卡住實際使用」或「守住正確性」的擴充。維持「與 MLIR
> 同構、靜態形狀、零依賴」這三個核心；不為功能完整而新增語法。每一項都要有
> 可驗收的測試，且不得讓既有範例或數值結果回歸。
>
> **完成記錄：**
> * v1.1 **已實作**：e2e 測試不再靜默跳過（工具鏈缺失＝跳過、程式失敗＝測試
>   失敗，可用 `MLR_REQUIRE_E2E=1` 強制）；新增 CI（`.github/workflows/ci.yml`，
>   Linux CPU + macOS MPS，設 `MLR_REQUIRE_E2E=1`）；checker 支援多錯誤累積
>   （每個函式一則、依原始碼順序輸出，`--check` 一次列出；同一函式內仍回報
>   第一個）。MPS 的 GPU 測試僅在 macOS 上執行。
> * v1.2 **已實作**：可微控制流——`scf.if`（雙分支反向、以第二個同條件的
>   `scf.if` 回報分支對外部值的條件貢獻）、`scf.for` 累加器模式（反向迴圈 +
>   body 重放，攜帶值只能線性累加）、`tensor.extract`（散射伴隨）與
>   `tensor.insert`（透過伴隨）。順帶修了三個既有正確性問題：
>   `tensor.insert` 在輸入被多次使用時破壞值語意（bufferize 補拷貝）、
>   scalar `mlr.add` 產生非法 MLIR、`tensor.zeros` 改為無 region 的
>   `mlr.zeros`；`examples/lib` 補上 fixture（改用 repo 相對路徑）。e2e 測試
>   以全域鎖序列化，避免小機器上並行 OOM。
> * v1.3 **已實作**：多檔編譯——`use "relative/path.mlr"`（相對於所在檔案的
>   目錄、遞迴載入、迴圈偵測、平坦命名空間；重複定義由 checker 既有的重複
>   檢查回報，`src/module.rs`）；函式形狀常數泛型——`fn f<N: i64>`，N 可作
>   張量維度與 body 內的值（`0..N`），呼叫端 `f<4>(...)` 逐實例單態化
>   （mangled `f.N.4`，重複呼叫共用實例；checker 於 `instantiate`，並修正
>   `check_func` 會清空呼叫端 scopes/cur_ret 的問題）。完整元素型別泛型
>   刻意延後（`doc/mlr.md` "Not implemented"）。
> * v1.4 **已實作**：MPS 反向的 `mlr_matmul_grad`（兩個 GEMM，轉置 operand
>   先打包進暫存 buffer；無 GPU 時退回 CPU 版，數值與 CPU 逐 byte 一致；
>   `mlr_conv2d_grad` 仍在 CPU——im2col 反向的收益與風險比不高，記錄在
>   「不做」）；可選平行——`MLR_THREADS=N`（預設 1）把 `mlr_matmul` 的
>   row 迴圈切給 N 個 pthread，按列分割、結果與執行緒數無關（訓練範例
>   逐 byte 驗證）；基準 `scripts/bench.sh` + `examples/bench/bench.mlr`
>   （512³ matmul × 10：1 執行緒 ≈ 2.5 s、4 執行緒 ≈ 0.9 s、MPS ≈ 0.08 s）。
> * v1.5 **已實作**：沿軸縮減 `sum_axis`/`mean_axis`/`tmin_axis`/`tmax_axis`/
>   `argmin_axis`/`argmax_axis`（軸為編譯期常數參數）；`sort`/`argsort`
>   （插入排序，argsort 穩定）/`cumsum`（沿最後一軸，rank ≥ 1）；批次讀取
>   `mlr.load_batch<T>(path, row)`（raw 格式同 `load_runtime`，T 的第一維
>   是 batch 大小）。這些運算暫不可微（不在 AD 的 FORWARD 清單，呼叫會有
>   清楚錯誤）。
>
> 承接：[roadmap.md](roadmap.md)（v0.3）與 [lib.md](lib.md) §13 的「之後」
> 清單。

## 0. 指導原則

1. **不回歸**：任何變更都必須讓 `scripts/run_all.sh` 與 `cargo test` 維持
   全綠，且既有範例輸出逐 byte 不變；若必須改變，於該版本明確記錄。
2. **同構優先**：新語意要能對應到 MLIR 既有的模型（region／SSA／typed
   shape／memref）。避免引入 MLIR 沒有的「值種類」。
3. **靜態優先**：形狀與型別盡量在編譯期確定；動態能力只在真實需求出現時、
   以小範圍（shape guard）引入，不要一次全面動態化。
4. **真實需求驅動**：每個里程碑都要有一支能證明價值的範例或使用情境；沒有
   就用現有機制（shell 橋接、`exec`、Python 工具）解決。
5. **可獨立釋出**：每個版本自成一個可回退的切片，不綁死後續版本。

## 1. 路線總覽

| 版本 | 主題 | 為何優先 |
| ---- | ---- | -------- |
| v1.1 | 正確性與自動化 | CI 與 e2e 目前會「靜默跳過」；沒有它，後續全部不可信 |
| v1.2 | 可微控制流 | 最大語言缺口：被微分的函式目前只能是直線程式 |
| v1.3 | 模組化與重用 | 多檔／`use`、函式形狀泛型；examples 變大前的必要投資 |
| v1.4 | 效能 | MPS 反向、可選平行；模型放大時的瓶頸 |
| v1.5 | 資料與張量庫 | `load_batch`、沿軸縮減、`sort`/`cumsum`/`argsort` |
| v1.x | 動態形狀（跨版本研究） | 可變 batch／序列長度的真實需求才會啟動 |

建議順序即上表由上而下；v1.1 不依賴任何其他版本，應最先落地。

## 2. v1.1 — 正確性與自動化

### 問題

* 沒有 CI：`.github/` 不存在，全靠本機 `scripts/test.sh`。
* **e2e 測試會靜默跳過，甚至掩蓋真正的失敗**：`tests/compile.rs` 的 `run`
  輔助函式在 `scripts/run.sh` 不存在時回傳 `None`，但**在 `run.sh` 以非零
  狀態結束時也回傳 `None`**——也就是說，編譯出壞 MLIR、runtime 崩潰、數值
  錯誤，都會被當成「工具鏈不在」而跳過。這是最危險的一點。
* checker 只回報**第一個**錯誤（`Checker.error: Option<Error>`），修正後才看
  到下一個。

### 做法

1. **永遠區分「工具不在」與「程式失敗」**：測試開頭先用 `which`／`PATH`
   偵測 `mlir-opt`、`mlir-translate`、`clang`。
   * 工具不在：本機預設跳過（可用 `MLR_REQUIRE_E2E=1` 改成硬失敗）。
   * 工具存在：`run.sh` 任何非零狀態都 **panic**，不得回傳 `None`。
2. **CI**：新增 `.github/workflows/ci.yml`，兩條 job：
   * Linux（CPU）：安裝 `llvm`／`clang`，`cargo build --release`、`cargo test`、
     `scripts/run_all.sh`（只跑 `run.sh`）。
   * macOS（MPS）：安裝 Homebrew LLVM，跑 `cargo test` 與 `run_mps.sh` 的
     子集（Metal 不可用的機器自動退回 CPU，見 `runtime/mlr_runtime_mps.mm`）。
3. **多錯誤累積**：`Checker` 改為 `errors: Vec<Error>`，盡量繼續型別檢查，
   最後依 `Span` 排序輸出；`--check` 一次列出所有問題。

### 影響檔案

`tests/compile.rs`、`src/check.rs`、`src/main.rs`、`.github/workflows/ci.yml`、
`scripts/test.sh`、`scripts/run_all.sh`。

### 驗收

* CI 綠燈；刻意讓一支範例失敗時，CI 必須**紅燈**（補一個負向測試證明不再
  靜默跳過）。
* 一個含 3 個（分屬不同函式的）型別錯誤的程式，`--check` 一次列出 3 個、依
  原始碼順序；同一函式內仍回報第一個（之後可在 statement 層繼續細化）。
* 既有 `cargo test` 數量不減（v1.1 後為 47 + 3，見 §10）。

## 3. v1.2 — 可微控制流

### 問題

`value_and_grad` 目前要求被微分的函式是**直線程式**（見
[train.md](train.md) §4.4）：允許 `let`、domain ops、元素級 `map`、常數索引的
`tensor.extract`；**不允許** `for`、資料相關的 `if`、`reduce`、
`tensor.insert`。這使得「loss 內含迴圈或分支」的模型無法在語言內訓練，是最大
的語言級缺口。

### 做法

在 `src/passes/autodiff.rs` 把反向從「逐指令」擴充為「結構對結構」：

1. **`for`（`scf.for` 的靜態反向）**：把迴圈反向走訪，為每個 `iter_arg`
   配置梯度累加器；對迴圈 body 內使用的值做標準的反向傳播，最後把累加器
   接回迴圈前的值。迴圈的邊界是純量，長度可為執行期值（不需展開）。
2. **`if`（資料相關分支）**：兩分支各自反向，於合流後把梯度**相加**。
3. **`reduce`**：反向 = 對輸入的每个元素回填 body 的伴隨值（accumulate）。
4. **`tensor.insert`**：反向 = 索引處放 `dy`、其餘為零（scatter），再加
   passthrough 到原 tensor。
5. **checker 放寬**：`check_differentiable` 允許上述節點；仍拒絕
   `sample`／`argmax`（離散）與非 f32。

### 影響檔案

`src/passes/autodiff.rs`、`src/check.rs`（`value_and_grad` 規則）、
`src/build.rs`（mangle／匿名 struct 的多值回傳）、`runtime/mlr_runtime.c`
（`tensor.insert` 的 scatter 伴隨；若用既有 kernel 可省）、
`tests/compile.rs`、`tools/check_grad.py`。

### 驗收

* 有限差分測試：一個含 `for` 累加與一個含資料相關 `if` 的 loss，梯度與
  數值微分在 f32 精度內一致。
* `tools/check_grad.py` 增加對應案例，與 PyTorch 對照。
* 新增範例（例如 loss 內以迴圈做 gradient accumulation）能訓練收斂。
* 既有直線程式的梯度輸出完全不變。

### 風險

迴圈反向的迭代順序與累加器初始化最易出錯；先以「每步可回放」的小迴圈
（`for i in 0..4`）與有限差分鎖住正確性，再放大。

## 4. v1.3 — 模組化與重用

### 問題

目前 `mlr` 一次只吃一個檔案（`src/main.rs` 的單一 `<file.mlr>`），函式沒有
型別參數。examples 一旦互相引用就只能複製貼上；`adam_step` 之類邏輯會重複。

### 做法

1. **多檔／`use`**（先做）：
   * 語法 `use "relative/path.mlr"`，遞迴載入、以「平坦命名空間 + 重複定義即
     錯誤」合併 `struct` 與 `fn`；不做真正的 namespace（YAGNI）。
   * 驅動程式接受多個輸入檔或由 `use` 解析；以 `use` 圖做拓撲排序後合併成
     單一 `Program` 再進 checker。
   * 相對路徑以「目前檔案所在目錄」解析（與現有 examples 的資料路徑規則
     區分開，避免和 `scripts/run.sh` 的 cwd 規則混淆）。
2. **函式泛型**（後做，範圍收斂）：
   * 只支援 `fn f<N: i64>(...)`（形狀常數）與「元素型別參數」；
     於 build 階段**單態化**（monomorphize），不引入新的 runtime 機制。
   * 沿用既有 `tensor.empty<T>()`／`mlr.load<T>()` 的 `type_args` 管線。

### 影響檔案

`src/parser.rs`、`src/ast.rs`、`src/check.rs`、`src/main.rs`、
`src/build.rs`；新增 `src/module.rs`（載入與合併）。

### 驗收

* 把一個現有範例（如 `examples/lib/lib.mlr`）拆成 `use` 兩個檔案後，輸出
  逐 byte 不變。
* 重複定義、循環 `use`、找不到檔案都有清楚錯誤。
* 一個泛型函式（形狀常數）實例化兩種尺寸，MLIR 正確且通過 verifier。

## 5. v1.4 — 效能

### 問題

CPU runtime 單執行緒；MPS 只加速**前向**的 matmul／conv2d，**反向仍走 CPU**。
模型放大或步數變多時是瓶頸（見 [roadmap.md](roadmap.md) §5）。

### 做法

1. **MPS 反向**：在 `runtime/mlr_runtime_mps.mm` 補 `mlr_matmul_grad`、
   `mlr_conv2d_grad` 的 MPS 實作（以 `MPSMatrixMultiplication` 實作
   im2col 後的反向），維持與 CPU 版相同介面。
2. **可選平行（gated，預設關）**：以環境變數 `MLR_THREADS=N` 開啟 CPU kernel
   的多執行緒（獨立迴圈切分，不改數值順序以維持確定性）。預設單執行緒，
   避免在 CI 或小模型上反而變慢。
3. **基準**：新增 `scripts/bench.sh` 與一個固定形狀的 matmul／conv2d／
   training step 基準，量測前後差異；沒有量測提升就不合併。

### 影響檔案

`runtime/mlr_runtime_mps.mm`、`runtime/mlr_runtime.c`、`scripts/bench.sh`。

### 驗收

* 反向前後數值與 CPU 版一致（f32 精度內）。
* 基準顯示可量測的加速；單執行緒結果與 v1.3 逐 byte 相同。
* MPS 不可用時仍能退回 CPU（既有行為不變）。

## 6. v1.5 — 資料與張量庫

### 問題

訓練資料目前一次載入、固定順序切片；`train_mnist_full.mlr` 已用
`rand_permutation` + `rows` + `gather` 手動做 mini-batch。缺內建的資料疊代；
張量庫缺沿軸縮減與 `cumsum`／`sort`／`argsort`（[lib.md](lib.md) §13）。

### 做法

1. **批次讀取**（先做，貼合既有 runtime load）：`mlr.load_batch<T>(path, row,
   rows)` 以 raw 檔 + 檔頭在執行期讀取指定列，配合既有
   `rand_permutation` 即得 shuffle／batch，不需新的資料型別。
2. **沿軸縮減**：把 `sum`／`mean` 等擴充為可指定軸；以 region 版
   `reduce` 的既有語意為底，新增對應 kernel 與 checker 規則。
3. **`cumsum`／`sort`／`argsort`**：新增 domain op + kernel（`sort` 與
   `argsort` 同步實作，argsort 以穩定排序保證可重現）。

### 影響檔案

`src/check.rs`、`src/build.rs`、`src/passes/runtime_ops.rs`、
`runtime/mlr_runtime.c`、`doc/lib.md`、`doc/mlr.md`、`examples/`。

### 驗收

* 每個新函式都有範例與測試；`sort`／`argsort` 與 numpy 對照。
* `train_mnist_full.mlr` 改用 `load_batch` 後結果不變（或更好）。
* 更新 `doc/lib.md` 的狀態表。

## 7. 動態形狀（跨版本研究，需求觸發）

`doc/mlr.md` 的 "Not implemented (yet)" 明列：符號維度與等式約束、runtime
shape guard、完整的 one-shot bufferization（別名等價類）。這些彼此關聯：

* **符號維度 + 等式約束**：讓 `?` 在同一函式內能追蹤「相同維度」的身分，
  而不只是與靜態維度統一。
* **runtime shape guard**：在進入 kernel 前檢查實際形狀，錯誤時有明確訊息。
* **完整 one-shot bufferization**：目前是「最後使用即重用」的啟發式；升級為
  別名等價類分析後，才能安全支援更複雜的原地更新。

**啟動條件**：出現「可變 batch 大小／可變序列長度」的真實模型需求。
在此之前維持靜態形狀，不預先實作。

## 8. 非目標（v1.x 明確不做）

與 [doc/struct.md](struct.md)、[doc/lib.md](lib.md) §10、[roadmap.md](roadmap.md)
§7 一致；除非有具體需求，否則不排程：

| 不做 | 原因 |
| ---- | ---- |
| 字串型別（值、串接、讀回） | 動態長度 + 堆積生命週期，與靜態同構衝突；字面量 + `print` + shell 橋接已覆蓋 |
| ownership／borrow checker | 純值 + 無別名 + SSA last-use 已足夠管理記憶體 |
| trait／繼承／動態分派 | MLIR 靜態編譯，無 vtable |
| 預設平行化 | 現有模型規模無可量測痛點；只在 v1.4 以旗標提供 |
| 自訂 ODS dialect | `mlr.*` 以 generic 形式輸出已可用 |
| MPS 的 `conv2d_grad` | im2col 反向要自管 scatter 與遮罩，收益比不上 matmul 反向；等 CNN 級訓練真的有痛點 |
| `runtime_ops` 表驅動重構 | 純維護性；等大量新增 op 時再順勢做 |
| 非同步拷貝／同步 | 沒有對應硬體場景 |
| f16／bf16 儲存運算、複數 | 沒有場景 |

## 9. 相容性與版本規則

* 遵循語意化版本：v1.x **不得**破壞既有 MLR 原始碼；破壞性變更留到 v2.0。
* 需要更名或收緊語意時（例如 `tmax` 一名兩義，見 roadmap §7），先提供
  相容別名，於次一個 minor 標記 deprecation，v2.0 再移除。
* 每個版本同步更新：`README.md`、`README.tw.md`、`doc/mlr.md`、
  `doc/lib.md`（狀態表）、本文件（把已完成項目移到「完成記錄」）。
* `Cargo.toml` 版本與本文件標題一致（v1.0 起）。

## 10. 測試與 CI 策略

* 測試分層：
  * 單元／IR：`tests/ir.rs`（verifier 負向測試）。
  * 整合：`tests/compile.rs`（前端 → MLIR → 端到端輸出比對）。
  * 端到端：`scripts/run_all.sh`（14 範例 × CPU/MPS）。
* CI 必須安裝 `mlir-opt`、`mlir-translate`、`clang`，並在**工具存在時**把
  e2e 失敗視為失敗（修正 §2 的靜默跳過）。
* 每個新語言功能至少附：一個正向測試、一個負向測試（錯誤訊息）、以及
  若可微則一個有限差分／PyTorch 對照。
* 基準（v1.4）與數值回歸（訓練 loss／accuracy）納入 CI 的允許誤差比對。
